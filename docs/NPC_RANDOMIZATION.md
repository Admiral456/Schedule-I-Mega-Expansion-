# NPC randomization and individuality

## Native appearance

Use the S1API appearance pipeline rather than separate character models. The core helper selects unique appearance values using a save-scoped seed; the game-facing adapter applies them through the native NPCAppearance typed customization builder:

```csharp
protected override void OnCreated()
{
    base.OnCreated();

    NpcAppearanceProfileApplier.TryApply(Appearance, SavedAppearanceProfile);

    if (IsPhysical)
        Schedule.Enable();
}
```

The profile data is generated by `NpcAppearanceProfileRandomizer` in the game-independent core. It uses a save-scoped seed and stable NPC ID to create a unique descriptor from documented native avatar fields and asset-layer paths. The 42-person roster therefore has no duplicate descriptor before it reaches the game renderer.

### What is made unique

The profile varies gender, height, weight, skin tone, eye colour, hair colour/style, face expression, facial hair where applicable, shirt style/colour, pants style/colour, shoe style/colour and optional headwear. The helper searches a new deterministic candidate if a profile signature already exists. All 42 Harborline descriptors are covered by unit tests.

The game-facing adapter is now in `src/GameIntegration/NpcAppearanceProfileApplier.cs`. It maps the profile into S1API's native `NPCAppearance.Set<T>()`, `WithFaceLayer<T>()`, `WithBodyLayer<T>()` and `WithAccessoryLayer<T>()` calls and runs `Build()` once. It deliberately avoids a per-client random fallback because that could cause visual divergence in co-op. The selected resource paths still need a live-game render check.

This guarantees distinct appearance **descriptors within the expansion's own roster**. It cannot honestly guarantee that a custom resident never resembles any vanilla or third-party NPC until the live avatar settings can be compared against those characters in the installed game build. That external uniqueness check remains a release gate.

## Native customer drug preferences

The game-facing adapter must discover the available values from the installed runtime `DrugType` enum. It must not hardcode a list copied from an old game version.

The core helper is independent of Unity and receives:
- a save-scoped seed generated once by the host and persisted;
- stable namespaced NPC IDs;
- the valid runtime DrugType names.

It returns one affinity per available drug type. Every customer gets at least one strong favourite (0.70–1.00) and one strong dislike (-1.00 to -0.70). Other values vary. A vector is unique within the generated Harborline customer roster. If the installed build exposes too few drug types/combinations, generation fails closed rather than silently giving several customers the same profile.

The game-facing adapter enumerates the installed `S1API.Products.DrugType` values through `NativeDrugAffinityAdapter.GetRuntimeDrugTypeNames()`, generates the per-customer vector, maps names back to the native enum with `ToNativeAffinities()`, and passes those tuples to native `WithAffinities(...)` inside `WithCustomerDefaults(...)`. The documented S1API baseline enum exposes Marijuana, Methamphetamine, Cocaine, MDMA, Shrooms and Heroin; the running enum remains the source of truth. The regular Schedule I customer contract generator remains in charge of in-world offers, budgets, product availability and deliveries.

Do not confuse expansion-only online-order product tiers (`sime.product.batch.*`) with the native drug type enum.

## Seed ownership and multiplayer

The host creates one random seed per save slot before the Harborline roster is initialized. The seed and resulting affinity vectors must be stored in the expansion save. The adapter discovers the live game's DrugType enum values at runtime and maps each generated affinity to the native `WithAffinities(...)` call inside `WithCustomerDefaults(...)`; no drug enum members are hardcoded into the core helper. The host is the only authority allowed to create or migrate those values. A client joining later receives the same registered NPC prefabs and save state; it never calls a separate local roll for an already registered NPC.

The seed must not use or reset `UnityEngine.Random`, because doing so can perturb unrelated game systems and other mods. The core helper uses SHA-256 over the save seed, NPC ID, algorithm version and choice channel. Changing one NPC ID does not reroll every other resident.

## Tests required

- same save seed + same IDs + same DrugType catalog gives byte-for-byte equivalent assignments;
- changing the input order does not alter assignments;
- each customer has a favourite and a disliked type;
- no two Harborline customers share the same full affinity vector;
- too few DrugType values fails safely;
- co-op late join sees the host's values;
- save/load does not reroll appearance or affinity values;
- third-party mods that register additional products do not crash the generator.
